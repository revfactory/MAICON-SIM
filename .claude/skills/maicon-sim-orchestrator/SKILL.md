# MAICON 시뮬레이터 오케스트레이터

국방 AI 경진대회 본선 경기장(5 m × 3.5 m)을 Blender에 재현하고, UGV가 주행하는 **1080p / 30fps 데모 영상**을 산출한다.

## 실행 모드: 하이브리드

| Phase | 모드 | 이유 |
|-------|------|------|
| 0. 컨텍스트·연결 확인 | 인라인 | 재실행 분기 판별, Blender 연결 확인 |
| 1. 측량 | 서브에이전트 단일 | 좌표계는 단일 출처여야 일관성이 유지된다 |
| 2. 스크립트 작성 | 서브에이전트 **병렬** | 씬에 접속하지 않으므로 병렬이 안전하다 |
| 3~5. 빌드·검수·렌더 | 인라인 **순차** | Blender는 단일 가변 상태 — 병렬 실행 금지 |

### 이 하네스의 근본 제약

**Blender MCP는 살아있는 단일 Blender 인스턴스를 조작한다.** 두 에이전트가 동시에 `execute_blender_code`를 호출하면 오브젝트 이름 충돌·컬렉션 경합이 발생하고, 어느 쪽이 원인인지 추적할 수 없게 된다.

따라서 이 하네스는 **작성과 실행을 분리**한다:
- 빌드 에이전트는 `.py` 스크립트만 쓴다 (도구 목록에서 Blender MCP가 구조적으로 제외되어 있다)
- 오케스트레이터가 번호 순서대로 하나씩 실행한다
- `scene-inspector`만 실제 씬을 조회한다

부가 이점이 크다. 씬 전체가 스크립트에서 결정적으로 재생성되므로, Blender가 죽거나 씬이 망가져도 재빌드 비용이 거의 없다.

### 이 분리가 만드는 함정 — 실측값은 오케스트레이터가 제공한다

빌드 에이전트는 Blender를 볼 수 없다. 그래서 **씬의 실제 수치가 필요한 작업을 시키면 파일만 읽어 기하를 역산하려 들고, 그 계산이 발산해 응답 없이 멈춘다.** 실제로 세 에이전트가 연달아 워치독 타임아웃으로 중단됐다:

| 에이전트 | 멈춘 지점 | 실제로 필요했던 것 |
|---------|----------|------------------|
| track-surveyor | "23×9 전수 스윕" | 객체·건물 바운딩박스 겹침 3건 |
| cinematographer | "트레이 Z 범위 조회" | `Z [-0.032, 0.643]` 한 줄 |

**대책: 수치가 필요한 작업을 위임하기 전에 오케스트레이터가 Blender에서 직접 재서 프롬프트에 넣는다.** 겹침 전수 검사, 바운딩박스, 카메라 도달 범위, 투영 좌표는 전부 몇 줄짜리 조회로 즉시 나온다. 추론시키지 말고 **측정해서 건네라.** 프롬프트에 "파일을 읽어 역산하려 들지 마라. 아래가 실제 값이다"를 명시한다.

**mm 단위 수정 몇 개는 직접 처리하는 편이 낫다.** 에이전트 재기동 오버헤드가 이득보다 크다. 다만 스펙 파일을 고쳤으면 판독 이력에 근거를 남긴다.

### 오케스트레이터도 틀린다 — 반박을 받아들일 자리를 만들어라

도면 판독은 오케스트레이터만 할 수 있지만(에이전트는 이미지를 못 본다), 그렇다고 판독이 옳다는 보장은 없다. 실제로 "나란한 노란 두 줄"을 도로 양쪽 경계로 읽고 이중선화를 지시했는데, 실은 인접한 두 블록 각각의 경계선이었다. 그대로 갔다면 9개 섹터가 전부 도로를 밟았을 것이다.

이것을 잡은 것은 에이전트의 검산이었다. 그러므로:

- 에이전트가 **FAIL을 보고하면 먼저 그 근거를 검토**한다. 지시를 관철시키기 위해 "클램프해서라도 맞춰라"고 하지 마라
- 스펙 해석을 바꿀 때는 **기존 필드와의 모순을 확인**한다. `outer.role`("바깥쪽 경계선")이 이미 있는데 `style.note`("중심선")를 덧씌워 충돌을 만든 것이 이 사건의 근원이었다
- 판단을 뒤집었으면 **스펙에 철회 사실과 근거를 기록**한다. 다음 세션이 같은 오해를 반복하지 않는다

## 워크플로우

### Phase 0: 컨텍스트 확인

**0-1. 재실행 분기**

- `_workspace/` 없음 → **초기 실행** (Phase 1부터)
- 있음 + 부분 수정 요청 → **부분 재실행** (0-3 참조)
- 있음 + 전면 재구축 요청 → 기존 `_workspace/`를 `_workspace_{타임스탬프}/`로 이동 후 초기 실행

**0-2. Blender 연결 확인**

`get_scene_info`를 호출한다. `Could not connect to Blender`가 오면 코드를 고치지 말고 사용자에게 요청한다:

> Blender를 실행하고 N 패널 → BlenderMCP → Connect를 눌러 주세요.

연결 전에는 Phase 3 이후로 진행할 수 없다. 다만 **Phase 1~2(스크립트 작성)는 연결 없이 진행 가능**하므로, 사용자가 Blender를 준비하는 동안 병행한다.

**0-3. 부분 재실행 판별**

수정 요청을 스크립트 단위로 매핑하고, **의존하는 후속 단계까지** 재실행 대상에 포함한다. 이것을 빠뜨리는 것이 "고쳤는데 결과가 안 맞는" 가장 흔한 원인이다.

| 요청 | 재실행 대상 |
|------|-----------|
| 좌표 수정 | `00` → 전체 (좌표는 모든 것의 기반) |
| 차선·노면 | `10~30` → `80`(경로가 차선 위) |
| **포트홀 좌표·반경** | **`10` + `30` 반드시 함께** — 베이스 메시의 구멍(10)과 림(30)이 한 쌍이라, 한쪽만 고치면 구멍이 노출되거나 림이 허공에 뜬다 |
| 건물 | `40` |
| 객체 형태 | `50` (인스턴스는 메시 공유로 자동 반영) |
| 객체 배치 | `55` |
| 차량 | `70` → `80`(부품 이름 의존) |
| 주행 | `80` → `90`(컷이 timeline 의존) |
| 카메라·조명 | `90` |
| 렌더 설정 | `95` |

### Phase 1: 측량

`track-surveyor`를 단일 호출한다. 좌표계는 단일 출처여야 하므로 이 단계는 병렬화하지 않는다.

```
Agent(subagent_type: "track-surveyor",
      prompt: "도면 이미지와 track-geometry 스킬의 좌표 레퍼런스를 검증·정밀화하여
               _workspace/spec/track_spec.json과 _workspace/scripts/00_common.py를 산출하라.
               검산 규칙을 전부 통과시킬 것.")
```

산출된 `track_spec.json`을 직접 읽어 검산 규칙(START 좌상단, FINISH 우하단, 개수 23/2/2/9/3)을 확인한다. **여기서 통과하지 못한 스펙으로 Phase 2에 들어가면 모든 후속 작업이 그 위에 쌓인다.**

### Phase 2: 스크립트 병렬 작성

`track_spec.json`이 확정된 뒤, 단일 메시지에서 3개 에이전트를 **병렬 호출**한다. 이들은 씬에 접속하지 않으므로 병렬이 안전하다.

```
Agent(subagent_type: "track-builder",  prompt: "10/20/30 스크립트 작성")
Agent(subagent_type: "asset-modeler",  prompt: "40/50/60/70 스크립트 작성")
Agent(subagent_type: "scene-dresser",  prompt: "55 스크립트 작성")
```

완료 알림을 기다린다. 위임한 작업을 오케스트레이터가 중복 수행하지 않는다.

`motion-director`와 `cinematographer`는 이 단계에서 호출하지 않는다 — 각각 `UGV_*` 부품과 `timeline.json`에 의존하므로 선행 실행 이후에 호출한다.

### Phase 3: 순차 빌드 + 점진 검수

**반드시 순차로 실행한다.** 각 스크립트는 짧은 로더로 실행한다:

```python
exec(open("/Users/robin/Downloads/maicon-sim/_workspace/scripts/10_ground.py").read())
```

스크립트 본문을 `execute_blender_code`에 직접 넣지 않는다 — 길면 전송이 실패하고, 수정 후 재실행도 번거로워진다.

**실행 순서:** `00` → `10` → `20` → `30` → `40` → `50` → `60` → `55` → `70`

(`55_placement`가 `60_markers` 뒤인 것은 배치가 마커 보드를 필요로 하기 때문이다.)

**각 실행 직후:**
1. `print` 출력에서 생성 개수 확인
2. 시각 변화가 있으면 `get_viewport_screenshot`으로 확인
3. 주요 분기점(`20`, `40`, `55`, `70`)에서 `scene-inspector` 호출

**개수만으로 통과시키지 않는다.** 좌표가 100배 틀려도 개수는 맞는다. 스크린샷이 유일한 실질 검증 수단이다.

실패 시: 담당 에이전트에게 오류 메시지와 함께 수정을 요청하고, 해당 스크립트만 재실행한다. 다음 단계로 넘어가지 않는다 — 오류가 누적되면 원인 추적이 불가능해진다.

### Phase 4: 모션

`70_vehicle.py` 실행 완료 후 `motion-director`를 호출한다. `80_motion.py`를 실행하면 `timeline.json`이 실측값으로 생성된다.

실행 후 `scene-inspector`로 애니메이션을 검증한다 — 정지·후진 구간, 체크포인트 통과, 포트홀 회피, 바퀴 동기화.

### Phase 5: 시네마 + 렌더

`timeline.json` 확정 후 `cinematographer`를 호출한다. `90_camera.py` → `95_render.py` 순으로 실행한다.

**렌더는 3단계로 나눈다. 이 순서를 지키지 않으면 잘못된 룩으로 30분을 태운다.**

1. **테스트 스틸** — 대표 프레임 1장을 렌더해 룩을 확인한다
2. 사용자에게 스틸을 보여주고 승인을 받는다
3. **전체 애니메이션 렌더** — 예상 소요를 알리고 **명시적 확인을 받은 뒤** 실행한다

전체 렌더는 Blender를 수 분~수십 분 블로킹하고 그동안 MCP가 응답하지 않는다. 확인 없이 시작하지 않는다.

최종 산출: `output/maicon_demo.mp4`

## 데이터 흐름

```
도면 이미지
   └→ [track-surveyor] → spec/track_spec.json ─┬→ [track-builder]  → 10/20/30.py
                          scripts/00_common.py │→ [asset-modeler]  → 40/50/60/70.py
                                               └→ [scene-dresser]  → 55.py
                                                        ↓ 순차 실행 (오케스트레이터)
                                                    Blender 씬
                                                        ↓
                                     [motion-director] → 80.py → spec/timeline.json
                                                        ↓
                                     [cinematographer] → 90/95.py
                                                        ↓
                                              output/maicon_demo.mp4

                    [scene-inspector] ← 각 단계 직후 → qa/{NN}_report.md
```

## 디렉토리 구조

```
maicon-sim/
├── _workspace/
│   ├── spec/          track_spec.json, timeline.json
│   ├── scripts/       00~95_*.py
│   └── qa/            verify_result.json, {NN}_{module}_report.md
└── output/            maicon_demo.mp4, stills/
```

`_workspace/`는 삭제하지 않고 보존한다. 스크립트가 곧 씬의 소스 코드이므로, 이것이 있으면 언제든 재빌드할 수 있다.

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| Blender 미연결 | 사용자에게 실행·연결 요청. 코드로 우회하지 않는다. Phase 1~2는 병행 진행 |
| 스크립트 실행 오류 | 오류 메시지 전문을 담당 에이전트에게 전달하고 해당 스크립트만 재실행. 다음 단계로 넘어가지 않는다 |
| `.001` 접미사 발생 | `purge()` 누락. 담당 에이전트에게 추가 요청 후 재실행 |
| 좌표 불일치 | 스펙 오류인지 스크립트 오류인지 판단해 해당 담당에게 전달. 양쪽을 모두 의심한다 |
| 에이전트 산출 누락 | 1회 재요청. 재실패 시 해당 단계를 건너뛰되 **최종 보고에 누락을 명시** |
| 렌더 중 응답 없음 | 정상이다. 호출이 타임아웃되어 백그라운드로 전환돼도 **Blender 내부에서는 렌더가 계속된다.** 실패로 오인해 재실행하면 같은 렌더가 두 번 돌아 파일이 깨진다. 완료는 출력 파일의 존재·크기로 판별한다 |
| 서브에이전트 스톨(무진행) | 씬 수치를 추론하려다 멈춘 경우가 대부분이다. 산출 파일이 남았는지 먼저 확인하고(작성 후 보고 중 끊긴 경우가 있다), 없으면 **필요한 실측값을 프롬프트에 넣어** 재요청한다. 같은 프롬프트로 재시도하면 같은 지점에서 다시 멈춘다 |
| 검수 실패 항목 잔존 | 실패 항목을 최종 보고에 그대로 남긴다. 미해결을 해결로 보고하지 않는다 |

## 규모 원칙

Phase 2의 병렬 호출은 3개다. 이 도메인은 병렬화 이득이 제한적이다 — 실행이 어차피 순차이기 때문이다. 대규모 팬아웃을 시도하면 조율 비용만 늘고 씬 충돌 위험이 커진다. 사용자가 "철저히", "여러 안" 등을 명시적으로 요청한 경우에만 시안 병렬 생성(예: 카메라 워크 3안)을 고려한다.

## 테스트 시나리오

### 정상 흐름
1. 사용자가 "경기장 시뮬레이션 만들어줘" → Phase 0에서 `_workspace/` 없음 확인, Blender 연결 확인
2. Phase 1: track-surveyor가 스펙 확정 (객체 23, 포트홀 2, 배리어 2, 섹터 9, 체크포인트 3)
3. Phase 2: 3개 에이전트 병렬로 8개 스크립트 작성
4. Phase 3: `00`→`70` 순차 실행, 4개 분기점에서 검수
5. Phase 4~5: 모션 → 카메라 → 테스트 스틸 → 사용자 승인 → 전체 렌더
6. 예상 결과: `output/maicon_demo.mp4` 생성, `qa/` 리포트 6건

### 에러 흐름 (부분 재실행)
1. 사용자가 "건물이 너무 낮아, 높여줘"
2. Phase 0-3에서 `40` 단독 재실행으로 판별 (후속 의존 없음)
3. asset-modeler에게 `HEIGHTS` 테이블 수정 요청 → `40_sectors.py` 재실행
4. scene-inspector 검수 → 톱 뷰·측면 뷰 스크린샷 확인
5. 예상 결과: 건물만 갱신, 다른 요소 무변경. 렌더는 사용자가 요청할 때만 재실행

### 에러 흐름 (좌표 오류)
1. Phase 3 검수에서 "SEC_04 좌표 Y 부호 반전" 발견
2. scene-inspector가 스펙 측 오류로 판단 → track-surveyor에게 전달
3. `track_spec.json` 수정 → 좌표 변경이므로 `40`, `55`, `80`을 재실행 대상으로 판별
4. 순차 재실행 후 재검수
