# 프로시저럴 에셋 — 건물 · 객체 · 마커 · 차량

모든 에셋은 외부 파일을 불러오지 않고 **Blender Python으로 생성**한다. 이유는 재현성이다. 씬이 스크립트에서 결정적으로 재생성되면 크래시나 실수의 비용이 0에 가까워진다. 에셋 라이브러리 의존은 그 성질을 깨뜨린다.

에셋 스케일의 기준은 **경기장 5 m × 3.5 m 실측**이다. 이 크기 안에서 UGV는 약 0.2 m, 객체는 0.03~0.16 m, 건물은 0.35~0.55 m다. 즉 전체가 축소 모형(디오라마)의 비율이며, 이 사실이 룩 전체를 지배한다 — 실물 건축이 아니라 **모형처럼 보이는 것이 정답**이다.

## 1. 공통 제작 원칙

**형태보다 실루엣.** 데모 영상에서 객체는 대부분 수십 픽셀 크기로 나온다. 표면 디테일에 폴리곤을 쓰는 대신, 멀리서도 종류가 구분되는 실루엣에 투자한다. 전차는 납작한 차체 + 포신, 적군은 세로로 긴 인형, 미사일은 뾰족한 원뿔 — 이 세 가지가 겹쳐 보이지 않으면 성공이다.

**베벨은 필수.** 완벽한 직각 모서리는 빛을 받지 않아 CG처럼 보인다. 모든 하드서피스 에셋에 0.5~1.5 mm 베벨을 준다. 이 한 가지가 렌더 품질에 가장 크게 기여한다.

```python
bev = obj.modifiers.new("Bevel", 'BEVEL')
bev.width = 0.0008        # 0.8 mm
bev.segments = 2
bev.limit_method = 'ANGLE'
bev.angle_limit = 0.523   # 30°
```

**머티리얼은 공유한다.** 오브젝트마다 새 머티리얼을 만들면 수백 개가 쌓여 씬이 무거워지고 일괄 수정이 불가능해진다. `get_or_create_material()`로 이름 기반 재사용한다.

**원점을 바닥에 둔다.** 오브젝트 원점이 중심에 있으면 배치할 때마다 높이의 절반을 더해야 하고, 이 계산 실수가 "물체가 땅에 반쯤 묻힘"의 원인이 된다. 생성 시 정점 Z를 `0 ~ h` 범위로 만들어 원점이 바닥에 오게 한다.

## 2. Sector 건물 (`40_sectors.py`)

도면의 사각형은 타워의 **바닥 풋프린트**이고, 실물은 고층 타워다 (참조 사진). 각 섹터는 대형 1동 + 부속 1동으로 구성된다.

| 요소 | 값 |
|------|-----|
| 대형동 풋프린트 | 0.16 ~ 0.22 m 정사각에 가깝게 |
| 대형동 높이 | 0.35 ~ 0.55 m (섹터마다 다르게) |
| 부속동 | 대형동의 60% 크기, 높이 40~60% |
| 색 | 콘크리트 회색 `(0.42, 0.42, 0.40)` |
| 기단(base) | 풋프린트보다 10 mm 넓게, 높이 8 mm, 밝은 회색 |

**높이를 섹터마다 다르게 주는 것이 중요하다.** 전부 같으면 스카이라인이 평평해 오비탈 샷의 인상이 약해진다. 섹터 번호를 시드로 결정적 변주를 준다 (`Math.random` 대신 — 재실행 시 형태가 바뀌면 재현성이 깨진다):

```python
HEIGHTS = {1: 0.42, 2: 0.51, 3: 0.38, 4: 0.47, 5: 0.55,
           6: 0.44, 7: 0.36, 8: 0.49, 9: 0.40}
```

**창문 표현** — 개별 창을 지오메트리로 만들면 폴리곤이 폭발한다. 세로 홈(그루브)을 벽면에 넣고, 머티리얼의 이미시브 스트라이프로 창문 띠를 표현한다. 참조 사진의 타워도 세로 스트라이프 패턴이다.

```python
# 벽면 세로 홈: 박스를 여러 개 겹치지 말고 Array 모디파이어로
arr = groove.modifiers.new("Array", 'ARRAY')
arr.count = 6
arr.relative_offset_displace = (2.4, 0, 0)
```

건물 상단에는 옥상 구조물(작은 박스 1~2개)을 얹는다. 밋밋한 직육면체와 실루엣이 확연히 달라진다.

## 3. 객체 7종 (`50_objects.py`)

각 종류를 **프로토타입 1개씩** 만들어 `04_Objects` 컬렉션 밖의 숨김 컬렉션(`_Proto`)에 둔다. 배치는 `55_placement.py`가 링크드 듀플리케이트로 복제한다. 프로토타입 방식이면 "전차 모양을 고쳐줘"가 프로토타입 1개 수정으로 끝난다.

| 종류 | 키 | 크기 (m) | 형태 요약 | 색 |
|------|-----|---------|---------|-----|
| 미사일 | `missile` | 0.16 × 0.03 × 0.03 | 원통 + 원뿔 노즈 + 후미 핀 4장, 받침대 위 경사 | 올리브 + 적색 밴드 |
| 위험물 | `hazmat` | 0.05 × 0.05 × 0.07 | 드럼통(원통 + 상하 링) | 노랑 + 검정 위험 표식 |
| 박격포 | `mortar` | 0.07 × 0.07 × 0.09 | 경사 포신 + 삼각 받침대 | 짙은 올리브 |
| 전차 | `tank` | 0.14 × 0.07 × 0.06 | 납작 차체 + 포탑 + 긴 포신 + 궤도 | 카키 |
| 적군 | `enemy` | 0.04 × 0.04 × 0.10 | 세로 인형 실루엣 (몸통+머리) | 짙은 적갈색 |
| 탄약상자 | `ammo_box` | 0.08 × 0.05 × 0.04 | 모서리 보강 박스 + 손잡이 | 올리브 그린 |
| 자동차 | `vehicle` | 0.12 × 0.06 × 0.05 | 차체 + 캐빈 + 바퀴 4 | 회청색 |

**색으로 구분되게 한다.** 전부 군용 올리브로 칠하면 영상에서 서로 구분되지 않는다. 위험물은 노랑, 적군은 적갈색처럼 채도 차이를 준다 — 실제 대회에서도 객체 인식은 색과 형태 양쪽에 의존한다.

## 4. ArUco 마커 보드 (`60_markers.py`)

참조 사진에서 노면에 세워진 흰 판 + 검은 마커다. 실제 대회 환경과 동일하게 재현한다.

- 판 크기: 0.05 × 0.05 m, 검은 테두리 프레임 + 하단 A자 스탠드
- 마커 패턴: **텍스처가 아니라 지오메트리 또는 절차적 이미지로 생성**한다. 외부 이미지 파일에 의존하면 재현성이 깨진다

마커 패턴은 `bpy.data.images.new()`로 픽셀 버퍼를 직접 채워 만든다. ArUco 4×4 딕셔너리 형태를 흉내 낸 6×6 격자(테두리 1칸 검정 + 내부 4×4 비트)면 시각적으로 충분하다:

```python
img = bpy.data.images.new(f"ARU_{i:02d}_tex", width=64, height=64)
px = [0.0] * (64 * 64 * 4)
# bits: 4x4 불리언 배열을 마커 ID에서 결정적으로 생성
for gy in range(6):
    for gx in range(6):
        black = (gx == 0 or gy == 0 or gx == 5 or gy == 5) or not bits[gy-1][gx-1]
        v = 0.0 if black else 1.0
        # 해당 격자 칸(약 10.67px)을 v로 채움
img.pixels = px
```

마커 ID는 객체 종류와 연결한다 (`ARU_11` = 11번 포지션, 마커 비트는 객체 종류 ID를 인코딩). 데모 영상에서는 읽히지 않아도 되지만, 규칙이 있으면 나중에 인식 파이프라인을 붙일 때 그대로 쓸 수 있다.

마커 보드는 **객체와 함께 배치**한다. 실제 경기장이 그렇고, 1인칭 샷에서 마커가 보이는 것이 이 대회의 시각적 정체성이다.

## 5. UGV 차량 (`70_vehicle.py`)

경기 플랫폼은 지상 무인차량 1대다. 크기 약 **0.20 × 0.13 × 0.09 m** (차선 폭 0.30 m 안에 들어와야 한다).

구성 부품과 이름 (애니메이션이 이 이름으로 부품을 찾으므로 정확히 지킨다):

| 이름 | 내용 |
|------|------|
| `UGV_Root` | 빈 오브젝트. 모든 부품의 부모. 경로 애니메이션은 이것에만 적용 |
| `UGV_Body` | 차체 (베벨 박스 + 경사 전면) |
| `UGV_Wheel_FL/FR/RL/RR` | 바퀴 4개. 로컬 X축 회전으로 굴림 |
| `UGV_Sensor` | 상단 LiDAR/카메라 마운트 (원통 + 렌즈) |
| `UGV_Cam` | 전방 카메라 위치의 빈 오브젝트. 1인칭 샷 카메라가 여기 붙는다 |

`UGV_Root`를 두는 이유는 애니메이션과 모델링의 분리다. 루트만 경로를 따라가고 부품은 그 아래 고정되면, 나중에 차체 디자인을 바꿔도 애니메이션이 그대로 산다.

`UGV_Cam`은 참조 사진의 시점과 맞춘다 — 차체 전방 상단, 노면에서 약 0.07 m 높이, 약간 아래를 향한 각도(-8°). 이 위치가 1인칭 샷에서 차선 두 줄과 마커 보드가 함께 잡히는 시점이다.

바퀴는 차체와 별도 오브젝트여야 한다. 하나로 합치면 굴릴 수 없고, 굴러가지 않는 바퀴는 데모 영상에서 즉시 눈에 띈다.

## 6. 배치 (`55_placement.py`)

`scene-dresser`가 담당한다. `track_spec.json`의 `objects` 배열을 읽어 프로토타입을 링크드 듀플리케이트로 복제한다.

```python
proto = bpy.data.objects[f"_PROTO_{kind}"]
inst = proto.copy()          # 메시는 공유 (link=True 효과)
inst.data = proto.data       # 명시적으로 메시 데이터 공유 — 메모리 절약
inst.name = f"OBJ_{pos['id']:02d}_{kind}"
inst.location = (pos["pos"][0], pos["pos"][1], 0.0)
inst.rotation_euler = (0, 0, pos.get("yaw", 0.0))
link_to(inst, "04_Objects")
```

메시 데이터를 공유하면 23개 인스턴스가 메모리를 거의 쓰지 않고, 프로토타입 수정이 전체에 즉시 반영된다.

**배치 규칙:**
- 객체는 **노면 위**(Z=0)에 놓인다. 원점을 바닥에 두었으므로 Z 오프셋은 0이다
- 같은 종류가 인접 포지션에 몰리지 않게 분산한다
- yaw는 포지션마다 다르게 준다 (전부 정면이면 배열된 것처럼 부자연스럽다). 포지션 ID에서 결정적으로 계산: `yaw = (pos_id * 37) % 360 * pi / 180`
- 각 객체 옆 0.04 m 지점에 대응 마커 보드를 배치한다

배치 후 반드시 확인: **23개 전부 생성되었는가**, **경기장 밖으로 나간 것이 없는가**, **건물이나 차선과 겹치지 않는가**. 겹침은 톱 뷰 스크린샷에서 바로 보인다.

## 7. 재작업 지침

- "전차가 이상해" → `_PROTO_tank`만 수정하고 `50_objects.py` 재실행. 인스턴스는 메시를 공유하므로 자동 반영된다
- "건물이 너무 낮아" → `40_sectors.py`의 `HEIGHTS` 딕셔너리만 수정
- "객체 위치를 바꿔줘" → `track_spec.json`의 `objects`를 고치고 `55_placement.py` 재실행
- 스케일 지적을 받으면 개별 에셋이 아니라 **비율 전체**를 점검한다. 차선 폭 0.30 m 대비 UGV 0.20 m, 객체 0.03~0.16 m의 관계가 무너지면 축소 모형의 설득력이 사라진다
